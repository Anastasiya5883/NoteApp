# Импорт метаданных 1С и проверка реквизитов — дизайн

## Цель

Добавить в личный кабинет пользователя раздел «Информация из локального конфигуратора», в котором можно загрузить стандартную XML-выгрузку конфигурации 1С в ZIP-архиве, увидеть состояние загруженных данных и использовать их при подборе объектов и реквизитов для технического задания.

Дополнительно приложение использует явно обозначенный неполный справочный каталог распространённых объектов 1С:ERP Управление предприятием 2 редакции 2.6.1.16 (обозначенной пользователем как 2.6.116). Справочник служит резервным источником и не представляется пользователю как полная точная копия конфигурации.

## Пользовательский сценарий

1. Пользователь открывает личный кабинет.
2. В верхней части кабинета доступны вкладки «История анализов» и «Информация из локального конфигуратора».
3. Во второй вкладке пользователь загружает ZIP, созданный из каталога стандартной команды конфигуратора «Конфигурация → Выгрузить конфигурацию в файлы».
4. Приложение проверяет архив, извлекает метаданные и сохраняет нормализованный каталог для текущего пользователя.
5. После успешной загрузки раздел показывает наличие данных, имя и версию конфигурации, имя файла, дату загрузки и сводные счётчики.
6. Пользователь может заменить или удалить загруженную структуру.
7. При анализе ТЗ в режиме «Подобрать реквизиты 1С» приложение сверяет найденные сущности и реквизиты сначала с локальной структурой, а затем со справочным каталогом ERP.
8. Результат явно указывает источник каждого совпадения и не смешивает точные локальные данные со справочными предположениями.

## Источники метаданных и приоритет

Приоритет источников:

1. Загруженная локальная структура пользователя — точный источник для текущей базы.
2. Встроенный справочный каталог ERP 2.6.1.16 — неполный резервный источник распространённых объектов.
3. Текущие эвристические словари анализатора — используются для извлечения кандидатов из текста, но не подтверждают существование объекта или реквизита.

Если локальная структура загружена, отсутствие элемента в ней имеет больший вес, чем наличие элемента в справочном каталоге. В интерфейсе это отображается как «не найдено в локальной конфигурации; присутствует в справочнике ERP».

## Поддерживаемый входной формат

Принимается один файл с расширением `.zip`. В корне архива или в единственном оборачивающем каталоге должен находиться `Configuration.xml`. Рядом могут находиться `ConfigDumpInfo.xml` и каталоги объектов стандартной XML-выгрузки 1С.

Первая версия импортирует:

- имя, синоним и версию конфигурации;
- справочники;
- документы;
- регистры сведений, накопления, бухгалтерии и расчёта;
- отчёты и обработки;
- перечисления, константы и бизнес-процессы;
- реквизиты объектов;
- табличные части и их реквизиты;
- измерения, ресурсы и реквизиты регистров.

Формы, макеты, права, роли, команды, модули BSL и содержимое информационной базы не сохраняются. Это уменьшает объём данных и исключает попадание исходного кода и возможных секретов в хранилище.

Ограничения первой версии:

- размер ZIP — не более 50 МБ;
- суммарный распакованный XML — не более 250 МБ;
- не более 50 000 файлов в архиве;
- запрещены абсолютные пути, `..`, символические ссылки и выход из логического корня архива;
- обрабатываются только XML-файлы, необходимые для заявленных типов метаданных;
- повреждённый, зашифрованный или не соответствующий выгрузке архив отклоняется целиком.

## Нормализованная модель

```ts
interface ConfigurationCatalog {
  configurationName: string
  configurationSynonym: string | null
  configurationVersion: string | null
  sourceFileName: string
  uploadedAt: number
  objects: ConfigurationObject[]
}

interface ConfigurationObject {
  kind: MetadataObjectKind
  name: string
  synonym: string | null
  attributes: ConfigurationAttribute[]
  tableParts: ConfigurationTablePart[]
}

interface ConfigurationAttribute {
  name: string
  synonym: string | null
  typeDescription: string | null
  role: 'attribute' | 'dimension' | 'resource'
}

interface ConfigurationTablePart {
  name: string
  synonym: string | null
  attributes: ConfigurationAttribute[]
}
```

Поиск выполняется без учёта регистра и с нормализацией `ё/е`, пробелов и технических разделителей. Техническое имя и синоним индексируются отдельно; исходные значения сохраняются для отображения.

## Хранение и API

В SQLite добавляется одна актуальная запись каталога на пользователя. Повторная загрузка атомарно заменяет предыдущую структуру. История версий каталога в первую версию не входит.

Серверные операции:

- `GET /api/configuration-catalog` — статус и нормализованный каталог текущего пользователя;
- `PUT /api/configuration-catalog` — загрузка ZIP, проверка, разбор и атомарная замена;
- `DELETE /api/configuration-catalog` — удаление структуры текущего пользователя.

Архив передаётся как `multipart/form-data`. Исходный ZIP после успешного разбора не сохраняется. В базе хранится нормализованный JSON и сводные счётчики. Все операции требуют действующую пользовательскую сессию и ограничиваются `user_id`.

## Интерфейс личного кабинета

Вкладка показывает один из трёх состояний:

- «Данные не загружены» — зона загрузки и краткая инструкция по созданию ZIP;
- «Загрузка и обработка» — блокировка повторной отправки и индикатор;
- «Данные загружены» — зелёный статус, сведения о конфигурации, дата и счётчики объектов, реквизитов и табличных частей.

Для загруженной структуры доступны кнопки «Заменить данные» и «Удалить данные». Удаление требует подтверждения. Ошибки формата, лимитов, сети и сервера выводятся рядом с зоной загрузки и не удаляют ранее сохранённый корректный каталог.

## Сверка при анализе

Анализатор продолжает извлекать из ТЗ кандидаты объектов и реквизитов. Новый слой сопоставления получает результат анализа и доступные каталоги и формирует проверки:

```ts
type MatchStatus =
  | 'local-exact'
  | 'local-similar'
  | 'erp-reference-exact'
  | 'erp-reference-similar'
  | 'missing'

interface MetadataCheck {
  requestedObject: string
  requestedAttribute: string | null
  status: MatchStatus
  matchedObject: string | null
  matchedAttribute: string | null
  source: 'local' | 'erp-reference' | null
  note: string
}
```

Точное совпадение проверяется по техническому имени и синониму. Похожее совпадение допускается только после нормализации и при высокой строковой близости; оно всегда помечается как предположение. Реквизит проверяется внутри сопоставленного объекта, включая реквизиты табличных частей с отображением пути `Объект.ТабличнаяЧасть.Реквизит`.

В результатах режима подбора появляется блок «Проверка по конфигурации». При отсутствии локальных данных отображается пояснение, что проверка выполнена только по неполному справочному каталогу ERP. При наличии локальных данных показывается дата актуальности структуры.

## Справочный каталог ERP

Репозиторий не содержит и не скачивает нелицензионную полную поставку 1С:ERP. Встроенный каталог — небольшой поддерживаемый JSON с распространёнными объектами и реквизитами, необходимыми для типовых сценариев текущего анализатора. В интерфейсе и типах он называется «справочный каталог», а не «базовая конфигурация».

Каждая запись содержит тип объекта, техническое имя, отображаемое имя, реквизиты и при необходимости табличные части. Каталог можно заменить полным легальным экспортом ERP 2.6.1.16 позднее без изменения API сопоставления.

## Ошибки и безопасность

- ZIP разбирается на сервере, а не в браузере.
- До распаковки проверяются количество записей, объявленные размеры и пути.
- Во время распаковки контролируется фактически прочитанный объём для защиты от ZIP-bomb.
- XML разбирается без DTD и внешних сущностей.
- Новая структура сохраняется только после полного успешного разбора.
- Сообщения пользователю не содержат серверных путей или XML-фрагментов.
- Удаление пользователя в будущем должно каскадно удалять его каталог; текущая схема использует внешний ключ на `users`.

## Тестирование

Модульные тесты покрывают:

- поиск `Configuration.xml` в корне и одном оборачивающем каталоге;
- разбор каждого поддерживаемого типа объекта, реквизитов и табличных частей;
- нормализацию имён и точное/похожее сопоставление;
- приоритет локального каталога над справочным ERP;
- отклонение ZIP traversal, ZIP-bomb, повреждённого XML и превышения лимитов;
- сохранение прежнего каталога при неуспешной замене.

API-тесты проверяют изоляцию пользователей, статусы GET/PUT/DELETE, авторизацию и атомарную замену. Клиентские тесты проверяют состояния вкладки и отображение результата сверки. Полная проверка включает `npm test` и `npm run build`.

## Вне объёма первой версии

- автоматическое подключение к работающей базе или конфигуратору 1С;
- хранение исходного ZIP или модулей BSL;
- история загруженных версий;
- сравнение двух конфигураций;
- определение, является ли объект типовым или доработанным;
- полный встроенный каталог ERP без легально полученной эталонной выгрузки;
- изменение конфигурации 1С из ассистента.
